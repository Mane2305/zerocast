# Architecture

Two phases:
- **Phase 1 — local:** everything runs on a laptop (CPU). Same code paths as production, with
  local adapters.
- **Phase 2 — production (free tier):** frontend on Vercel, backend/model on Modal, database and
  file storage on Supabase. Only adapters and config change.

## Big picture

```
Browser (Next.js)
  ├─ DuckDB-WASM: read CSV/Excel/Parquet → map columns → aggregate to template → Parquet
  ├─ Demo pages read precomputed JSON from /public/demo (no backend call)
  └─ REST calls (contracts/openapi.yaml)
        │
FastAPI backend
  ├─ /datasets   store Parquet, run health check
  ├─ /jobs/*     create background jobs (forecast, review, factors), poll status
  ├─ JobRunner   Phase 1: in-process single model worker │ Phase 2: Modal function
  ├─ Storage     Phase 1: local folder                   │ Phase 2: Supabase Storage
  ├─ DB          Phase 1: SQLite (SQLAlchemy)            │ Phase 2: Supabase Postgres
  └─ YugEngine   loads the model once; the ONLY module that imports yug
```

## Backend

- Python 3.11, FastAPI, Pydantic v2, SQLAlchemy 2, pandas/pyarrow, numpy, statsmodels, `holidays`.
- Yug pinned to the PR #14 commit until it is merged (see YUG_NOTES.md).
- **YugEngine** (`backend/app/engine/`):
  - Loads `YugPipeline.from_pretrained("birlaailabs/yug")` once at startup.
  - All model calls go through **one worker** (a queue) — the pipeline is not safe for concurrent
    calls (upstream issue #9).
  - Returns per-step quantiles **and** horizon-total distributions computed from sample paths.
  - Records latency for every call (used by "Under the hood").
- **Services** (pure functions, unit-tested, no I/O): health check, insights (scenarios, target
  probability, capacity risk, risk scores, trust horizon), year-in-review, factor check.
- **JobRunner interface**: `submit(job_type, params) -> job_id`, `status(job_id)`. Jobs report
  progress 0–100 and store results as JSON.
- **Storage interface**: `put(key, bytes)`, `get(key)`. **Repository** for datasets, jobs, annotations.
- Config via environment variables (`ZC_ENV=local|prod`, `ZC_DB_URL`, `ZC_STORAGE=local|supabase`,
  `ZC_DEVICE=cpu|cuda`, `ZC_NUM_SAMPLES=100`).
- Tests: pytest. Model-dependent tests use a **tiny random Yug model** (same pattern as the yug
  repo's `tests/conftest.py`) so they run in seconds without downloading weights.

## Frontend

- Next.js (App Router) + TypeScript, Tailwind, shadcn/ui, TanStack Query, TanStack Table,
  ECharts (fan charts), DuckDB-WASM, SheetJS for Excel.
- API client generated from `contracts/openapi.yaml`. A **mock server** generated from the same
  file (e.g. Prism) lets the frontend be built before the backend exists.
- App shell: top bar with module links, breadcrumb title, theme toggle. No permanent sidebar.
- Patterns: empty state with numbered steps · Parameters → Run → Result · problem tabs with
  counts · quantified warning banners · KPI cards with "complete / limited data" labels.
- Demo data: `frontend/public/demo/<demo_id>/*.json`, generated by the backend's
  `precompute_demos` script.

## Phase 2 mapping (no code changes outside adapters/config)

| Concern | Phase 1 | Phase 2 |
|---|---|---|
| Frontend hosting | `next dev` | Vercel (Hobby) |
| API + model | `uvicorn` on laptop | Modal (web endpoint + function, scale to zero) |
| Jobs | in-process worker | Modal `spawn` + job rows in Postgres |
| DB | SQLite file | Supabase Postgres |
| Files | `./storage/` | Supabase Storage |
| Demo results | `public/demo` | same (static on Vercel) |

## Performance budget (measured on a 2-core CPU, random weights, PR #14 code)
- Univariate, context 2048, horizon 28: ~0.15 s per series.
- Univariate, horizon 256, 100 samples: ~1.2–1.7 s.
- Covariates (2), horizon 48, 100 samples (PR #14): ~0.4 s.
Re-measure on the target machine and keep the limits in PRODUCT.md consistent with it.
